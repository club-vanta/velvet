# Guest Identity — Mazmo Optional (Frontend) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Match the frontend to the backend's guest-identity rework (`alter-tracker-backend` PR #15): guests can now exist without a Mazmo account, every guest path param changed from a numeric `mazmo_user_id` to a UUID `guest_id`, and staff gain manual guest creation, Mazmo link/unlink, guest editing, and server-side guest search.

**Architecture:** Two waves over the same set of pages. Wave one (Tasks 1-5) is a straight parity migration — regenerate types, then fix every call site that breaks because a field got renamed, became nullable, or a path param changed shape. Nothing new is user-visible yet; the app should look identical to today once wave one lands, just pointed at the new contract. Wave two (Tasks 6-9) adds the net-new capabilities the backend now supports, all scoped to `GuestsPage.tsx`. Task 10 is manual verification against the real local backend.

**Tech Stack:** React 19, TypeScript, Vite, TanStack Query v5, `openapi-fetch` with types generated from the backend's OpenAPI schema, shadcn/ui v4 (`base-nova` style) built on Base UI, Tailwind v4, Vitest + Testing Library, sonner for toasts.

**Spec:** `docs/superpowers/specs/2026-08-10-guest-identity-mazmo-optional-frontend-design.md`

## Global Constraints

- **Never hand-edit `src/api/types.ts`.** It is generated by `npm run generate:api`.
- **Primitives are Base UI, not Radix.** Import from `@base-ui/react/*`. Snippets from Radix-era shadcn docs will not compile.
- **Every user-facing string goes through `useLanguage()`.** Add the key to **both** the `en` and `es` blocks of `src/lib/i18n.tsx`. `TranslationKey` is `keyof typeof translations.en` and `t()` indexes `translations[lang]`, so a key missing from `es` is a type error.
- **`t()` takes a key and nothing else — there is no interpolation.** Compose dynamic text in JSX, e.g. `{t("editGuestDialogTitle")} {guest.displayname}`.
- **Admin gate is `const isOrgAdmin = isSiteAdmin || activeOrg?.role === "ADMIN"`**, where `isSiteAdmin = user?.role.name === "SITE_ADMIN"`. `GuestsPage.tsx` and `MeetupDetailPage.tsx` already compute this — do not recompute it differently.
- **Approved-user gate vs. org-admin gate — do not conflate them.** Ban/unban require `isOrgAdmin`. Edit, link-mazmo, and unlink-mazmo require only an approved (logged-in, approved) user — every staff member, not just admins. This is a backend authorization fact, not a frontend style choice; getting it backwards either locks staff out of something they're allowed to do, or is purely cosmetic (the backend enforces it either way) but misleads whoever reads the UI as documentation of who can do what.
- **Mutation error handling:** always `throw new Error(extractApiError(error, "<fallback>"))` in `mutationFn` (or a specific status-code message where the endpoint has meaningfully different failure modes, matching the existing `AddGuestDialog` pattern), and `onError: (err: Error) => toast.error(err.message)`.
- **Guest identity going forward is `guest.id` (a UUID string), never `guest.mazmo_user_id`.** `mazmo_user_id` and `mazmo_handle` are both `string | null` / `number | null` now — every read of either needs a null check. `guest.id` is never null.
- **Spanish copy:** the app uses club slang for some terms (`banned` → "Vantear"/"Vanteado"). Guest-identity terms (link, unlink, edit) have no established slang — use plain, literal Spanish.
- **Commit hooks run `tsc --noEmit`, Prettier, and ESLint.** A commit fails if any of them fail. Run `npx prettier --write <files>` before committing if the format check trips.
- **This branch is `feat/guest-identity-mazmo-optional`.** The design spec is already committed there. Keep working on this branch; do not create a new one.

Create `src/hooks/useDebouncedValue.ts`:

```ts
import { useEffect, useState } from "react";

/**
 * Returns `value`, delayed by `delayMs` of no further updates. Unlike
 * `useDeferredValue`, this actually defers work (e.g. a network request)
 * rather than just deprioritizing a render.
 */
export function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);

  return debounced;
}
```

```ts
import { useDeferredValue, useState } from "react";

export function useGuestSearch<T>(
  items: T[] | undefined,
  getFields: (item: T) => { displayname: string; mazmoHandle: string | null },
): {
  search: string;
  setSearch: (v: string) => void;
  filtered: T[] | undefined;
} {
  const [search, setSearch] = useState("");
  const q = useDeferredValue(search).trim().toLowerCase();

  // When items is undefined the data is still loading — pass it through as-is
  // so callers can distinguish "loading" (undefined) from "no results" (empty array).
  // Only run the filter once we have actual data and a non-empty query.
  const filtered = q
    ? (items ?? []).filter((item) => {
        const { displayname, mazmoHandle } = getFields(item);
        return (
          displayname.toLowerCase().includes(q) ||
          (mazmoHandle ?? "").toLowerCase().includes(q)
        );
      })
    : items;

  return { search, setSearch, filtered };
}
```
